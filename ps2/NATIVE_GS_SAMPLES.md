# Box3D PS2 visual sample bring-up: native GS + GIF

Run `sh ps2/build_ee.sh` with PS2DEV and PS2SDK installed. Start
`ps2/box3d_ps2_samples.elf` in PCSX2. No gsKit is used.

- Boot: `BOX3D_SAMPLE_START`, then `BOX3D_GS_READY` after CRT and double VRAM allocation.
- A native GS GIF frame clears the screen to dark navy and draws the ground
  grid, axes and moving box edges. No pixels are generated by `scr_printf`.
- The physics runner automatically cycles between Box Stack (12 boxes),
  Inclined Plane (5 boxes) and Spinning Books (3 boxes), every 600 frames.
- The packet encoder sends `GS_REG_FRAME_1/PRIM/RGBAQ/XYZ2` and related
  setup registers through GIF packed A+D on DMAC GIF channel 2; GS FINISH
  is waited before switching read-circuit framebuffer at VBlank.
- 320 x 224 pixel resolution, 2 x PSMCT32 framebuffer, no textures or
  Z-buffer in this first pass. Default physics mode is scalar C17.

This is an intentional subset of the desktop samples, not the full
Sokol/ImGui application. A correct physics log but black video usually
means GS initialization/GIF/coordinate setup needs fixing. First verify
the GS stage or provide a PCSX2 screen and the console log.

Source: `ps2/sample_native.c`, `ps2/gs_native.[ch]`.
PS2SDK APIs used for display-mode initialization: `graph_initialize`,
`graph_set_mode`, `graph_set_screen`, `graph_set_framebuffer`;
DMA: `dma_channel_initialize`, `dma_channel_send_normal`,
`dma_channel_wait`. Everything else in the rasterization pipeline
is low-level GS packet assembly.

**PCSX2 validation:** the tester provided a rendered screenshot of the
wireframe stacking sample on 2026-10-10 and reported it runs at 60fps.
This establishes real PS2 EE Box3D stepping plus native GS GIF wireframe
output on PCSX2, not performance of physical PS2 silicon.

## New optional GS filled triangles + hardware depth test

The build now also creates `ps2/box3d_ps2_samples_solid.elf`. It uses
the same Box3D physics sample runner but compiles the GS renderer with
`-DBOX3D_GS_SOLID=1`. The **previous** `box3d_ps2_samples.elf` remains
the regression-safe wireframe reference and is not silently replaced.

Solid mode allocates an additional aligned 320x224x32-bit Z buffer
using `graph_vram_allocate`, programs GS `ZBUF_1` and `TEST_1`
through raw GIF A+D, clears depth to zero per frame with a GS SPRITE,
then switches to `ZTST=GREATER_EQUAL` with higher Z assigned to nearer
vertices. Each non-ground cuboid sends 12 GS `PRIM=TRIANGLE` primitives
with a fixed directional ambient+diffuse color from its Box3D quaternion;
the ground grid and optional edges remain native GS lines. The renderer
waits for `GS_FINISH` and VBlank before swapping color buffers as
before. No gsKit, PS2SDK draw library, VU microcode, textures, or
C++/ImGui runtime is involved.

The first solid implementation does not do full near-plane triangle
clipping or perspective-correct depth interpolation; large or
camera-intersecting triangles may be rejected entirely. This is a
rendering bring-up, not a production mesh renderer.

**Status:** filled/Z-buffered GS ELF has not yet been crosscompiled
or executed in PCSX2. Verify separately from the already confirmed
wireframe screenshot; if solid fails, run the old
`ps2/box3d_ps2_samples.elf` and report logs/screenshots.

## Official-demo-inspired GS edition

In PCSX2 the tester confirmed `box3d_ps2_samples_solid.elf` produces
filled solids with correct Z occlusion. The new executable
`ps2/box3d_ps2_samples_official.elf` builds as an additional variant,
leaving both the previous wireframe and filled implementations intact.

The PC desktop sample uses a Preetham atmospheric sky, PBR/IBL materials,
sun shadows, GTAO, exposure/AgX tonemapping and an ImGui UI. The PS2
cannot run these graphics shaders in their current form, so this build
implements a carefully scoped low-cost GS approximation:

- A blue-to-hazy-daylight gradient sky using GS native Gouraud
  interpolated `PRIM=TRIANGLE` (IIP=1), without a texture.
- A pale, softly alternating checker ground of 12x12 two-triangle tiles,
  with discrete fine GS lines to resemble the official procedural grid.
- Opaque cuboids with muted daylight materials and directional face
  diffuse + ambient shading, maintaining original Box3D transforms.
- A projected planar shadow quad for every eligible cuboid,
  blended with `GS_SET_ALPHA` and depth writes disabled. This
  approximates but does not reproduce the original cascade shadow maps.
- A small semi-transparent sample-selection-style HUD on the left.
  The characters are a custom 5x7 bitmap emitted as raw GS sprites,
  with no IOP font service, gsKit, libdraw or textures.
- Hardware Z-testing, two PSMCT32 color buffers, the same physics
  stepping and scene switching as the confirmed working solid edition.

The draw packet grows from 2,048 to 8,192 quadwords in this edition
to cover the checker floor and GUI primitives. GS channel-2 DMA and
per-frame FINISH/VBlank synchronization remain unchanged.

```sh
git pull --ff-only origin experiment/ps2-ee-scalar
sh ps2/build_ee.sh
# Boot ps2/box3d_ps2_samples_official.elf in PCSX2
```

The scene fidelity is deliberately approximate: it does not support
image-based lighting, proper PBR BRDFs, arbitrary triangle near-clipping,
SSAO, real shadow maps, or ImGui. The displayed sample bodies are still
the simplified C17 ports, not byte-for-byte duplicates of every original
desktop scene. Some geometries may flicker or disappear near the camera,
and 60fps is unverified for this more expensive renderer.

**The official-inspired edition is new and not yet crossbuilt or
PCSX2-validated.** The previous GS-filled sample remains the fallback
if any rendering or performance regression occurs.

The official-style first Box Stack also restores the **full 40 dynamic
boxes**, original 1.25m vertical spacing, 40m half-extent ground,
and approximately the original 40° yaw / 15° pitch / 50m orbit camera
looking at Y=20. The previously validated wireframe/filled builds
still use 12 boxes and their smaller scene camera. This changes
physics/rendering load; 60fps must be re-evaluated in the new ELF.

## Diagnosing shadow fragments on the inclined-plane screenshot

Two user-provided PCS​​X2 screenshots confirmed native GS filled
triangles and the later official-inspired daylight edition, but the
official-inspired shadow quads appeared as small broken fragments.
The previous `render_shadows` had *two structural problems*:

1. It projected **only the four bottom-face corners** of each rotated
   box onto `y=0`, so the shadow silhouette was incomplete. The
   shadow of a hovering tilted platform in particular cannot be modeled
   by its bottom face alone.
2. It supported **only the horizontal floor**, and drew shadow quads
   before the opaque geometry. Shadows on the tilted platform were
   impossible, and depth interactions were fragile.
   Triangles crossing the view near-plane were rejected in full,
   producing missing sections.

The separate `ps2/box3d_ps2_samples_shadows.elf` fixes this without
changing the older ELFs:
- `shadow_project.[ch]` projects all eight box corners in the direction
  of the sun, computes a monotone-chain **convex silhouette hull**, and
  clips it to the finite receiver plane with Sutherland-Hodgman.
- Receivers are the *actual Box3D ground top face* and, in the incline
  scene, the *upper face of the rotated platform* using its quaternion.
  Each resulting polygon is one triangle fan, preventing within-box
  alpha overdraw. Ground shadow bounds are matched to the 48m checker.
- GS submission occurs **after opaque geometry**, using the already
  populated native GS ZBUF32 and depth test to apply shadows only over
  visible receivers. `ZMSK=1` avoids damaging scene depth.
  A 0.045m normal offset prevents Z-fighting; GS alpha blending makes
  the silhouettes translucent.
- GS triangles are clipped to the camera near plane before projection,
  instead of dropping an entire triangle because one point was too near.
- `BOX3D_SHADOW_RECEIVERS` logs the number of receivers, generated
  shadow hulls and emitted triangles periodically.

Host-only geometry regression (does not need PS2DEV):
```sh
cc -O2 -std=c17 -Wall -Wextra -Werror -pedantic \
  ps2/shadow_project.c ps2/shadow_project_test.c -lm \
  -o /tmp/box3d_ps2_shadow_test
/tmp/box3d_ps2_shadow_test
```

**This is still directional projected geometry, not a true stencil
shadow-volume implementation or render-to-texture depth shadow map.**
The included PS2-era articles describe real alternatives: the "Shadow
of the Colossus" graphics lecture describes VU1-generated simplified
shadow volumes and stencil-style self-shadowing; the "Onimusha 3"
engine lecture describes low-resolution projected shadow textures
smoothed with GS bilinear filtering plus less costly substitutes.
GS does not expose a direct PC-style multibit stencil buffer or a
programmable shadow depth comparison. Achieving arbitrary receiver
self-shadowing requires a distinct shadow-mask/volume pass or another
multipass treatment of GS framebuffer-alpha and depth behavior.

The projected-shadow ELF has not yet been crosscompiled or executed
under PCSX2, unlike the earlier daylight GS visuals. Verify that
`hulls` and `triangles` are nonzero and that the large inclined
platform's full shadow now appears on the floor. 60fps is **not**
assumed for this more complex edition.

## Kawase-style native GS ping-pong soft shadows (experimental)

The screenshots of the initial Z-buffered projected-shadow ELF show that
some shadows are intact but others disappear (especially around tilted
or ground-intersecting bodies). Two independent improvements were pushed:

1. `shadow_project.c` now constructs the clipped above-plane box from
   all 8 vertices **plus 12 edge-plane intersections**, before directional
   projection. The previous code dropped below-plane vertices without
   inserting new silhouette vertices. A penetrating-box regression was
   added to the C17 portable shadow projector test.
2. A separate `ps2/box3d_ps2_samples_softshadows.elf` applies a native GS
   **Dual Kawase-style** blur to its projected, occlusion-tested shadow
   coverage, without gsKit or shaders:
   - After opaque rendering, draw Z-tested RGB coverage into an offscreen
     full-res 320x224 PSMCT32 VRAM mask, ZMSK=1 (original scene depth intact).
   - GS TEX0/TEX1 + hardware bilinear filters downsample
     320x224 -> 160x112 -> 80x56 using independent VRAM surfaces.
   - GS fixed-function additive RGB blending does four shifted bilinear
     taps per pass, then upsample 80x56 -> 160x112 and refine in a
     second 160x112 ping-pong buffer.
   - Return to the color framebuffer; composite four filtered taps
     with `GS_SET_ALPHA(2,0,2,1,16)`, subtracting a blurred **RGB coverage
     map** from the already-rendered color. GS alpha does *not*
     accumulate like RGB, so blurring RGB rather than attempting to
     blur the alpha channel is intentional.
   - All five offscreen buffers are disjoint, sized within 4MiB PS2
     VRAM. Each texture read is preceded by `GS_REG_TEXFLUSH`.
     No EE-side readback or CPU convolution.
   - Shadow silhouettes still use the depth-tested receiver geometry,
     so this is **not** a full shadow map, stencil volume or arbitrary
     self-shadowing implementation.

Build and compare these independently:
```sh
git pull --ff-only origin experiment/ps2-ee-scalar
sh ps2/build_ee.sh
# PCSX2:
# ps2/box3d_ps2_samples_shadows.elf       (hard receiver shadows)
# ps2/box3d_ps2_samples_softshadows.elf   (Kawase-style soft receiver shadows)
```

The soft ELF emits `BOX3D_KAWASE_FRAME` every 120 steps with raw EE CP0
Count ticks for physics and render+VBlank, versus a nominal 60Hz budget
of 4,915,200 ticks/frame. It also keeps `BOX3D_SHADOW_RECEIVERS` logs.
The timings include emulator pacing and GIF DMA completion; they are
not a direct GPU cycle profiler and do not prove PS2 silicon throughput.

**New pipeline is untested with PS2DEV or PCSX2.** Potential bring-up
risks include GS texture cache coherency, blend semantics, incorrect
UV/XY sampling offsets, and blurred silhouettes bleeding a few pixels
across depth discontinuities. Older hard-shadow / no-shadow ELFs remain
available. PCSX2 screenshots and console timing logs are needed before
claiming the effect renders or keeps 60fps.

### Approximate GS VRAM budget, PSMCT32

The GS soft edition uses PS2SDK's page-aligned VRAM allocator (in 32-bit
words), with widths rounded to a 64-pixel TBW multiple. The approximate
allocation is:

| Render target | Allocation in 32-bit words |
| --- | ---: |
| Two 320x224 color buffers | 143360 |
| One 320x224 depth buffer | 71680 |
| Full resolution 320x224 shadow coverage | 71680 |
| Two 160x112 half-resolution ping-pong surfaces | 45056 |
| Two 80x56 quarter-resolution ping-pong surfaces | 16384 |
| **Total** | **348160 words (1,392,640 bytes)** |

This remains under the PS2's 4MiB GS local memory limit, leaving room for
more detailed meshes, textures, light masks and screen-space passes.
The final HUD explicitly prints `SOFT GS KAWASE` in this variant so
screenshots cannot be confused with the hard-shadow edition.

## Shadow disappearance and occlusion diagnostics (2026-10-10)

Tester PCSX2 screenshots show that the old receiver-shadow edition still
has holes while the original soft-shadow edition shows **no visible
shadows**. Neither build is classified as correct. The current two
investigations are separate:

- **Hard receiver-shadow geometry/depth:** box/receiver intersections
  are now included in the silhouette hull. A further fix switches
  `BOX3D_GS_RECEIVER_SHADOWS` to perspective-correct **inverse depth**
  for the GS hardware Z test. Linear camera distance Z was invalid
  across perspective-projected triangles: the checker floor and the
  shadow polygon use different triangulations of the same physical plane,
  so GS interpolation could reject shadow triangles even when they
  exactly align with the receiver. The new `1/z` encoding preserves
  GS `ZTST=GEQUAL` and Z clear=0. Legacy sample ELFs are unchanged.
- **Soft GS VRAM ping-pong path:** a separate
  `ps2/box3d_ps2_samples_softdebug.elf` places three real GS-rendered
  offscreen textures near the bottom of the screen, explicitly labeled
  `RAW`, `QUARTER`, `FINAL`. These identify whether the problem is
  in the shadow mask, half/quarter downsample, or the final RGB
  subtraction composite. This is a **native GS display of actual VRAM
  surfaces**, not synthetic debug graphics or CPU readback.

Recommended test order after `sh ps2/build_ee.sh`:

1. `ps2/box3d_ps2_samples_shadows.elf`: confirm the enlarged solid
   shadows no longer fragment against checker floor / inclined receiver.
2. `ps2/box3d_ps2_samples_softdebug.elf`: inspect the actual `RAW`,
   `QUARTER`, `FINAL` thumbnails. A visible RAW but black FINAL
   points to blur/texture sampling; a visible FINAL with no shadow
   on the scene points to composite/blend settings; black RAW indicates
   projection/Z-mask generation still fails.
3. `ps2/box3d_ps2_samples_softshadows.elf`: only evaluate final
   quality/frame rate after the first two work.

These editions remain unverified on the user's R5900/PCSX2 after these
fixes. Do not claim the geometry or blur bug is fixed until the tester
shows the new screen and, ideally, the `BOX3D_SHADOW_RECEIVERS` CSV.

## PCSX2 shadow mask failure recovery: receiver-layered pipeline

Tester screenshot still showed fragmented receiver silhouettes with the
GS depth-driven approach, and RAW/QUARTER/FINAL masks mostly black in
the Kawase debug edition. The earlier "inverse Z" adjustment was not
sufficient: the real-world multi-receiver depth approach and render
order were still rejecting shadow coverage.

The new pipeline is **receiver-layered**:

- Draw the *opaque floor*.
- Generate and composite its full clipped projected shadow mask without
  GS depth testing (shadows can only exist inside its finite receiver).
- Draw the *opaque inclined slab*, if present. It naturally occludes
  shadows that belong behind its surface.
- Generate and composite its own clipped shadows, also without the
  problematic Z-test.
- Draw the *dynamic bodies last*, restoring their full opaque Z-tested
  depth and silhouettes over the shadows.

Both hard shadows and full VRAM soft-shadow passes now use this order.
Every `b3GsShadowEnd` restores `TEST_1` to GEQUAL for the next
opaque geometry. The soft path still performs full/half/quarter/half
GS TEX0 bilinear ping-pong; final fixed-function RGB subtraction is
strengthened from FIX=16 to FIX=28 so a complete silhouette remains
visible through the soft kernel. No CPU convolution, gsKit, shaders or
Sokol is involved.

This should produce **complete RAW masks** without depending on subtle
Z comparisons between independently tessellated GS primitives.
It is not a physically perfect transparency-aware shadow mapping
technique: moving body self-shadowing is intentionally not attempted
in this receiver-ordered rendering pass. True self-shadowing remains
a separate VU1 volume/depth-texture project.

Testing:
```sh

```

## PCF-like full-resolution shadow filter (after PCSX2 Kawase feedback)

The tester's latest PCSX2 screenshot confirms the native GS RAW/QUARTER/
FINAL masks contain shadows and the full receiver-layered pipeline works,
but the Dual Kawase chain softens them too aggressively. The new opt-in
`ps2/box3d_ps2_samples_pcf.elf` bypasses ALL half/quarter ping-pong
stages during shadow compositing. It takes the already receiver-projected,
non-Z-tested **320x224 RGB shadow coverage mask** and reads it as a GS
TEX0 PSMCT32 texture with `TEX1` bilinear filtering and texture-cache
flush. The fixed-function GS alpha blender averages a compact 3x3
pattern with these per-tap weights (sum = 96):

```
    6  12   6
   12  24  12
    6  12   6
```

Nine full-resolution textured sprites use 1-pixel X/Y shifts and
`GS_SET_ALPHA(2,0,2,1,FIX)` with `FIX` equal to each weight. Since
coverage is encoded in RGB 0..128, this subtracts up to 96 RGB levels
on fully shadowed pixels and forms a compact ~1-2 pixel penumbra.
No EE pixel readback, no GLSL, gsKit, libdraw, libtexture or IOP helpers.

**Terminology:** This is *PCF-like post-filtering of a precomputed binary
coverage mask*, not depth-map percentage-closer filtering. Traditional
PCF compares receiver depth against a shadow-depth map per tap. GS has
no programmable per-texel depth comparison; a true depth-map PCF would
require an explicit GS multipass comparison design. Filtering after
geometry visibility is instead a deliberately sharp PS2-friendly
approximation.

Compare:
```sh
sh ps2/build_ee.sh
# box3d_ps2_samples_shadows.elf      hard reference
# box3d_ps2_samples_pcf.elf          new full-res 3x3 weighted filter
# box3d_ps2_samples_softshadows.elf  existing broad Kawase reference
```

Both use the same Box3D positions/casters/receiver order. GS HUD for
the new edition reads `GS PCF 3X3`, and stdout prints
`BOX3D_SHADOW_FILTER,PCF_MASK_3X3,...`. The PCF mode still allocates
the earlier shared half/quarter scratch buffers for layout simplicity
but does not sample or iterate over them.

**The new PCF ELF has not yet been crosscompiled/run in PCS​​X2; the
soft working screenshot validates only the older Kawase pipeline.**
